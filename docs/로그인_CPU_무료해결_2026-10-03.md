## 어느 처리가 CPU를 썼는가

공식 Native PBKDF2 상한100,000회 때문에 기존600,000회는 동일 결과를 내는 JS 라이브러리로 계산됩니다. 실제 temporary tail로 전체 요청 CPU와 완료한 단계만 수집했고, PIN·해시·토큰·headers·서명URL·오류 원문·학생 본문은 저장하지 않았습니다.

| 분리 검사 | 실제 결과 |
|---|---|
| 잘못된 기존 SHA256 PIN 거부 | HTTP401, Worker CPU3ms |
| 기존 SHA256 PIN→600,000회 PBKDF2 첫 변환 | 한 번 HTTP200, CPU1713ms. Free의 단발 여유로 성공했으나 지속 가능한 해결이 아님 |

## 구현과 보안 유지

- 계정·PIN 해시·일기·관계는 계속 D1, 사진은 계속 비공개 R2입니다. `PinKdf`는 Workers의 **비공개 Durable Object 바인딩**으로 계산만 하고 저장 API·세션 생성·계정 권한·타이머·검증 결과 캐시를 사용하지 않습니다. DO는 Free에서 지원하는 SQLite backend로 선언하지만 학생 자료를 그 저장소에 쓰지 않습니다.
- Worker가 D1에서 읽은 실제 계정 ID로 계산 객체를 정합니다. 브라우저의 이름·역할·학생 ID를 권한으로 신뢰하지 않습니다. 존재하지 않는 계정도 dummy KDF 뒤 거부하며 객체 키는256개 bucket으로 제한합니다.
- 같은 PBKDF2-HMAC-SHA256/600,000회/UTF-8 salt/256bit 출력입니다. 기존 해시와 호환하며 독립 Node crypto 출력·앞자리0·UTF-8 PIN·잘못된 PIN을 검사했습니다. 내부 계산 결과는32bytes 크기를 강제합니다. 공개 KDF API를 만들지 않았습니다.
- DO가 계산하는 동안 공개 Worker는 I/O를 기다립니다. 문서가 지원하는 별도 CPU 예산을 쓰며 강도를 낮추거나 인증 검사를 건너뛰지 않습니다. DO 내부 동기 루프는 라이브러리의 반복 시계 읽기·callback600,000회 비용을 줄이며 모든 KDF round와 라이브러리 정리는 그대로입니다.
- 로그인 시도 기록/시도 수/계정 조회를 atomic D1 batch로 묶고, 이미 PBKDF2인 credential의 불필요한 UPDATE를 제거했습니다. 생성한 token hash는 마지막 세션 재조회에서 재사용하지만 계정 활성·세션 만료 검사는 유지합니다.
- 경쟁 때문에 다시 읽은 credential이 정확히 이미 검증한 해시와 같으면 중복 KDF를 생략합니다. 달라졌으면 다시 검증하고 atomic session INSERT에서 활성 계정/현재 해시를 재검사합니다. 세션 생성에 실패하면 실패 시도 수를 지우지 않습니다.
- PIN 변경도 같은 비공개 계산 경로를 쓰며 기존 CAS·다른 기기 세션 해제를 유지합니다. private 일기/사진 교사 접근 금지·다른 반 차단·저장 재시도·수정 충돌을 실제 API suite에서 확인했습니다.
- 재배포 전에 로컬용 정적 bundle을 재사용했던 설정 오류를 수정했습니다. `deploy:trial`이 반드시 시험 bundle을 다시 빌드합니다. 원격 측정은 loopback config를 거부하고 원격 browser는 localhost 접근을 차단합니다. 운영 화면/CSS/사용 방법은 수정하지 않았습니다.
