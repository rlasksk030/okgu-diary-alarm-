# 자료 이전·전환·복귀 — 시험 준비

아직 실제 시트 헤더, 학생 자료와 Drive 원본 사진을 확보하지 않았습니다. 제공 Apps Script와 가상 자료 기준의 구현입니다. 실제 자료 반입·운영 변경에는 최종 승인이 필요합니다.

## 가상 자료에서 검증한 도구

- `migration/normalize.ts`: 검토한 헤더/계정 identity 대응표만 사용합니다. 숫자 PIN, 모호한 계정, 추가/누락 열은 중단합니다. 기존 SHA256/PBKDF2 해시와 앞자리 0을 보존합니다. ‘담임’ 칭찬은 학급 교사 그룹이며 로그인 계정을 새로 만들지 않습니다.
- `migration/d1.ts`: 결정적 ID, 일기·게시판·댓글/부모·좋아요·칭찬·교사 메모·사진 관계를 생성합니다. 초기 반입의 재실행은 INSERT ON CONFLICT DO NOTHING이며 기존 기록을 덮어쓰지 않습니다. 이것을 변화분 적용으로 사용하면 안 됩니다.
- `migration/delta.ts`: 이전/최신 원본과 반입 직후 target baseline, 현재 target의 차이를 비교합니다. 새 서버 수정/동일 ID 충돌/원본 누락은 검토 대상으로 차단합니다. 작은 승인된 변화분은 CHECK 제약의 사전 조건과 D1 atomic batch로 적용하며, 계획 후 target이 바뀌면 전체 롤백합니다. 새 v2 기록은 보존하고 같은 적용 ID의 재실행은 무해합니다.
- `npm run migrate:delta:rehearsal`: 격리된 가상 **로컬 D1/workerd**에서 변경, version 증가, 재실행, 계획 후 충돌의 전체 롤백을 확인합니다.
- 변화분은 무료 Worker의 50 query 한도에 맞춰 사전 조회 1 + 최대 49 statements로 제한합니다. 큰 변화분을 임의 분할하지 않습니다. 실제 규모가 확인된 뒤 관계 단위/쓰기 정지 절차와 필요한 유료 CPU/query 예산을 검토해야 합니다. 원본에서 사라진 자료를 자동 삭제하지 않습니다.
- 원본 알림/구독은 비공개 archive-only입니다. 이전만으로 실제 구독/예약 발송을 활성화하지 않습니다. 사진 변화분은 R2에 먼저 넣고 SHA256를 대조한 후 D1 참조를 바꿔야 합니다. 실제 Drive 다운로드/R2 이전 어댑터는 아직 미완료입니다.

## 암호화 백업과 격리 복원

로컬 가상 검증에서만 실행합니다. 키는 Codex 환경 secret에 `OKGU_BACKUP_KEY` 이름으로 64자리 hex(AES256)를 설정하고 별도 안전한 곳에 보관합니다. 채팅·Git·명령 결과에 키를 출력하지 않습니다.

```sh
npm run backup
npm run restore:rehearsal -- .local/backups/생성된파일.enc
```

D1 테이블은 하나의 batch에서 일관되게 읽습니다. 연결 사진과 ready upload의 원본/썸네일을 함께 암호화하며 파일 크기·SHA256를 기록합니다. 객체가 없으면 백업 성공으로 처리하지 않습니다. ready=0 업로드는 본문 관계로 사용되지 않으며 재시도가 필요합니다.

복원은 매번 새 `.local/restore-rehearsal/<시간>` 아래에 실행합니다. 현재 개발 DB나 운영 DB를 덮어쓰지 않습니다. 모든 테이블 값, 외래키 관계, 모든 R2 원본/썸네일의 체크섬을 비교합니다. 원격 복원 옵션은 차단합니다. 실제 운영 DB/R2 백업의 접근 방법, 동결 시점, 저장 위치·보존 기간·키 관리와 실제 크기는 승인 전에 확정해야 합니다.

## 승인 전 제시할 전환안

1. 실제 헤더와 명시적인 계정/행 identity를 읽기 전용으로 확인합니다. 기존 헤더 불일치 문서와 비교하고 대응표를 검토합니다. 원본 시트/Drive의 접근 제한 백업을 만듭니다.
2. 초기 자료를 격리 저장소로 반입하고 엔터티별 건수, 본문/줄바꿈, 날짜, PIN 형식, 댓글 부모, 공개 범위, 사진 관계/바이트 SHA256를 대조합니다. 같은 반입을 재실행합니다.
3. 시험 배포의 학생/교사/다른 반/개인 기록 ACL, 모바일/PWA, 13명 동시 성능과 CORS를 통과시킵니다. 현재는 로컬 검증이며 이 단계가 완료되지 않았습니다.
4. 최종 승인 후 짧게 기존 쓰기를 동결합니다. 원본/target 백업을 만들고 마지막 추가·수정 변화분과 새 사진을 적용합니다. 원본 누락/새 서버 수정 충돌은 사람이 해결합니다.
5. 운영 GitHub Pages 주소와 manifest identity를 유지한 채 승인된 API 연결만 전환합니다. 이전 세션/PIN 로그인 재검증, 오래된 PWA 업데이트 경로를 확인합니다.
6. 알림 전환은 **기존 GAS 예약 OFF 확인 → 새 D1 작업 ON** 순서로 합니다. 시험은 발송 차단/가상 transport만 씁니다. 기존 Vercel 운영 연결, 노출 키 rotation/재구독, 교사 댓글·칭찬·자기 계정 테스트를 확인한 뒤 실제 푸시를 별도 승인받습니다.

## 신규 자료를 잃지 않는 복귀

전환 후 새 DB를 옛 백업으로 덮어쓰면 신규/수정 기록을 잃습니다. 이상을 발견하면 새 쓰기를 잠깐 멈추고 **현재 D1 전체 + R2 원본/썸네일 + PIN/계정/관계**를 먼저 암호화 백업합니다. 반입 직후 baseline과 현재 target을 비교하여 신규/수정 자료를 보존 대상에 포함합니다.

기본 복귀는 안정된 이전 Worker 배포/화면 버전으로 돌아가면서 현재 D1/R2를 유지하는 방식입니다. DB 손상 시 별도 DB/R2에 백업을 복원·대조하고, 이후 신규/수정 자료를 충돌 검토 후 다시 적용합니다. 현재 도구는 격리 복원과 작은 D1 변화분까지 검증했으며, 운영 복귀 전체 자동화를 완료했다고 주장하지 않습니다.

완전히 옛 GAS/시트로 복귀하려면 새 기록/댓글/공개 범위/사진의 역방향 exporter와 승인된 반입 어댑터가 추가로 필요합니다. 새 PBKDF2 PIN을 원래 GAS의 SHA256 검증기가 읽을 수 없다는 차이도 처리해야 합니다. 이를 무시한 옛 PIN 복원이나 강제 PIN 초기화는 하지 않습니다. 원본으로 되돌릴 수 있다는 이유만으로 새 자료를 삭제하지 않습니다. 이 경로가 실제 검증되기 전에는 운영 전환을 승인 요청하지 않습니다.
